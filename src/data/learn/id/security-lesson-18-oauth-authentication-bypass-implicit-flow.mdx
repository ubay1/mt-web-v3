# OAuth 2.0: Bypass Autentikasi via Celah Implicit Flow & Client Tampering

Banyak aplikasi modern menyediakan opsi praktis **"Sign in with Google"**, **"Log in with GitHub"**, atau akun media sosial lainnya. Fitur ini dibangun di atas protokol **OAuth 2.0**. Namun, sering kali terjadi kesalahpahaman fundamental di kalangan pengembang: **OAuth 2.0 sejatinya dirancang untuk *Authorization* (Otorisasi akses data), bukan untuk *Authentication* (Membuktikan identitas pengguna)**.

Ketika pengembang memaksakan OAuth untuk proses login tanpa memahami implikasi keamanannya—khususnya saat menggunakan **Implicit Grant Type**—timbul celah fatal di mana penyerang dapat **mengambil alih akun pengguna lain (*Account Takeover*) hanya dengan memodifikasi satu baris data di Burp Suite**.

Materi ini membedah anatomi celah autentikasi OAuth 2.0 berbasis lab PortSwigger Web Security Academy: *Authentication bypass via OAuth implicit flow*, menjelaskan akar masalahnya di level arsitektur, panduan eksploitasi langkah demi langkah, hingga perbaikan kode backend secara defensif.

---

## 1. Konsep Kunci: Mengapa OAuth Sering Disalahgunakan?

Secara standar, OAuth 2.0 mendefinisikan interaksi antara tiga entitas utama:
1. **Resource Owner:** Pengguna pemilik data/akun.
2. **Client Application:** Website atau aplikasi kita (misal: Toko Online atau Web Blog) yang ingin mengakses data pengguna.
3. **OAuth Service Provider (IdP):** Penyedia layanan pihak ketiga (misal: Google, Facebook, Twitter) yang memiliki *Authorization Server* dan *Resource Server*.

### Perbedaan Dua Alur (Grant Types) Populer

| Tipe Alur | Alur Distribusi Token | Tingkat Keamanan |
| :--- | :--- | :--- |
| **Authorization Code Flow** | Server aplikasi menukar kode sementara (*code*) dengan access token secara langsung (*back-channel / server-to-server*). | **Tinggi (Standar Industri)** |
| **Implicit Flow (Legacy)** | Access token dikirim langsung ke peramban pengguna via hash URL (`#access_token=...`). Client JS memproses token secara lokal. | **Rentan (Ditinggalkan di OAuth 2.1)** |

> [!WARNING]
> **Masalah Utama Implicit Flow:** Token otorisasi terekspos langsung ke browser pengguna, peramban menyimpan token di memori atau URL history, dan client application bertanggung jawab mengabari servernya sendiri tentang siapa yang baru saja login.

## 3. Di Mana Letak "Bug"-nya? (Akar Masalah Kerentanan)

Celah ini muncul karena **asumsi keliru di sisi backend aplikasi web (*Client Application*)**:

### 1. Bagaimana Aplikasi Melakukan Login
1. Pengguna mengklik tombol *"Login with Social Media"*.
2. Browser dialihkan ke server OAuth penyedia, user memasukkan kredensial yang sah.
3. OAuth Provider mengembalikan access token ke browser melalui fragmen URL:
   ```http
   HTTP/1.1 302 Found
   Location: https://client-app.com/oauth-callback#access_token=vN3a0bL4c9...&token_type=Bearer
   ```
4. JavaScript di browser mengambil token tersebut, lalu memanggil endpoint `/userinfo` milik OAuth Provider untuk mengambil data profil:
   ```json
   {
     "id": "10923",
     "email": "wiener@normal-user.net",
     "name": "Wiener"
   }
   ```
5. Untuk mempertahankan sesi login pengguna, browser mengirimkan data ini ke backend aplikasi melalui request POST:
   ```http
   POST /authenticate HTTP/1.1
   Host: client-app.com
   Content-Type: application/json

   {
     "email": "wiener@normal-user.net",
     "username": "wiener",
     "token": "vN3a0bL4c9..."
   }
   ```

### 2. Kecerobohan Backend (Blind Trust)
Perhatikan apa yang dilakukan backend aplikasi target saat menerima `POST /authenticate`:
- Backend membaca `req.body.email`.
- Backend melihat ada parameter `token`.
- Backend **berasumsi** bahwa karena ada token yang dikirimkan, maka pengguna yang mengirimkan request tersebut adalah pemilik email `wiener@normal-user.net`!
- Backend **TIDAK PERNAH** memverifikasi ke OAuth Provider apakah token `vN3a0bL4c9...` tersebut memang benar-benar diterbitkan untuk `wiener@normal-user.net`.
- Backend **TIDAK PERNAH** memastikan apakah token tersebut cocok dengan email yang dikirimkan di payload.

> [!IMPORTANT]
> **AKAR MASALAH:** Parameter `email` dan `token` dikirimkan secara terpisah oleh browser (sisi client). Siapa pun yang mengontrol browser dapat memodifikasi isi JSON tersebut sebelum mencapai backend server!

## 5. Bedah Kode Backend: Mengapa Terjadi & Cara Memperbaikinya

### ❌ Implementasi Backend yang Rentan (Vulnerable Code)

Berikut adalah contoh tipikal kode backend Express.js yang melakukan kesalahan fatal ini:

```typescript
import express from 'express';
import { issueSessionCookie, findUserByEmail } from './auth-service';

const app = express();
app.use(express.json());

// ❌ RENTAN: Mempercayai data identitas (email) langsung dari request body client
app.post('/authenticate', async (req, res) => {
  const { email, username, token } = req.body;

  // Cacat fatal: Hanya memeriksa apakah token dikirim, tanpa memvalidasi keasliannya
  if (!token || !email) {
    return res.status(400).json({ error: 'Data otentikasi tidak lengkap' });
  }

  // Server langsung mencari user berdasarkan email yang dikirim penyerang!
  let user = await findUserByEmail(email);
  if (!user) {
    user = await createUser({ email, username });
  }

  // Menerbitkan sesi login untuk email tersebut tanpa validasi token
  const sessionToken = issueSessionCookie(user.id);
  res.cookie('session', sessionToken, { httpOnly: true, secure: true });
  return res.json({ status: 'success' });
});
```

---

### ✅ Implementasi Backend yang Aman (Defensive Code)

Pertahanan yang kokoh mewajibkan verifikasi token langsung ke server OAuth Provider di sisi server (*Server-to-Server Backchannel Verification*):

```typescript
import express from 'express';
import axios from 'axios';
import { issueSessionCookie, findUserByEmail, createUser } from './auth-service';

const app = express();
app.use(express.json());

const OAUTH_USERINFO_ENDPOINT = 'https://oauth-service-provider.com/userinfo';

// ✅ AMAN: Server memvalidasi token langsung ke OAuth Provider
app.post('/authenticate', async (req, res) => {
  const { token } = req.body;

  if (!token) {
    return res.status(401).json({ error: 'Token otorisasi wajib disertakan' });
  }

  try {
    // 1. Server menghubungi OAuth Provider secara mandiri menggunakan token
    const idpResponse = await axios.get(OAUTH_USERINFO_ENDPOINT, {
      headers: {
        Authorization: `Bearer ${token}`,
      },
      timeout: 5000,
    });

    // 2. Data identitas HANYA diambil dari respons resmi OAuth Provider, BUKAN dari client!
    const verifiedEmail = idpResponse.data.email;
    const verifiedUsername = idpResponse.data.username;

    if (!verifiedEmail) {
      return res.status(400).json({ error: 'Email terverifikasi tidak ditemukan di IdP' });
    }

    // 3. Terbitkan sesi berdasarkan email yang diverifikasi IdP
    let user = await findUserByEmail(verifiedEmail);
    if (!user) {
      user = await createUser({ email: verifiedEmail, username: verifiedUsername });
    }

    const sessionToken = issueSessionCookie(user.id);
    res.cookie('session', sessionToken, { httpOnly: true, secure: true, sameSite: 'lax' });

    return res.json({ status: 'success' });
  } catch (error) {
    // Jika token palsu, kedaluwarsa, atau dimanipulasi, IdP akan melempar 401 Unauthorized
    return res.status(401).json({ error: 'Validasi token gagal di sisi OAuth Provider' });
  }
});
```

## 6. Metodologi Bug Hunter: Menguji Celah OAuth di Program Bug Bounty

Saat kamu melakukan audit keamanan web atau berburu bug bounty pada fitur login OAuth:

1. **Pantau Lalu Lintas HTTP di Proxy:** Selalu petakan request dari awal (`GET /auth`) hingga penerbitan session cookie aplikasi.
2. **Cari Endpoint Autentikasi Internal:** Perhatikan apakah setelah proses login sosial selesai, ada request sekunder seperti `POST /oauth/callback`, `POST /api/v1/auth/social`, atau `POST /authenticate`.
3. **Periksa Payload Body:** Jika kamu melihat data profil (seperti `email`, `user_id`, `sub`, atau `account_id`) dikirimkan bersama `token`, ini adalah indikasi kuat adanya potensi celah!
4. **Lakukan Uji Manipulasi Parameter (Tampering):**
   - Ganti email ke target admin atau email korban lain.
   - Hapus parameter `token` (apakah server tetap mengizinkan?).
   - Ganti token dengan token kosong atau token dari akun lain.
5. **Cek Respons Server:** Jika respons berhasil mengembalikan sesi baru dengan identitas korban, kamu telah menemukan celah **Critical Account Takeover**!

## 7. Rekomendasi Standar Industri (OAuth 2.1)

1. **Tinggalkan Implicit Flow:** Konsorsium IETF dan OAuth Working Group secara resmi **mendeprekasi Implicit Grant pada OAuth 2.1**.
2. **Gunakan Authorization Code Flow dengan PKCE:** Untuk Single Page App (SPA) maupun aplikasi mobile, selalu gunakan **Authorization Code Grant yang dilengkapi dengan PKCE (*Proof Key for Code Exchange - RFC 7636*)**.
3. **Gunakan OpenID Connect (OIDC):** Untuk kebutuhan autentikasi identitas, gunakan OpenID Connect yang menyediakan **ID Token bertanda tangan digital (JWT tersignatur kriptografis)** sehingga client dan server dapat memverifikasi integritas klaim pengguna tanpa ragu.
