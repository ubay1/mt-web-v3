# Broken Access Control: User Role can be Modified in User Profile (Mass Assignment)

One of the most dangerous variations of _Broken Access Control_ is **Vertical Privilege Escalation**, where a standard user elevates their permission level to become an **Administrator**.

This flaw often stems from **Mass Assignment (Auto-Binding)**, a condition where the backend server automatically maps and writes all client-supplied JSON keys into the database model without enforcing strict property whitelisting.

---

## 1. Vulnerability Concept: How Does It Happen?

When a user updates their account profile (for example, changing their email address), the web client sends an HTTP request containing a JSON body:

```http
POST /my-account/change-email HTTP/1.1
Content-Type: application/json

{
  "email": "user@normal-user.net"
}
```

### Information Leakage in API Response
Upon updating, the backend inadvertently returns the entire user database entity:

```json
{
  "username": "wiener",
  "email": "user@normal-user.net",
  "apikey": "abcdef123456",
  "roleid": 1
}
```

From this response, an attacker discovers that user permission levels are controlled by an internal property named **`roleid`** (where `1` denotes standard users and `2` represents Administrators).

### Exploitation via Mass Assignment
Using **Burp Suite Repeater**, the attacker injects `"roleid": 2` into the email update request. If the backend blindly binds all request parameters to the ORM model, the database executes:

```sql
UPDATE users SET email = 'user@normal-user.net', roleid = 2 WHERE id = 101;
```

The attacker's account is instantly elevated to **Administrator**!

   ```json
     "roleid": 1
   }
   ```

---

### Step 5: Modify the Request Body in Repeater
1. Return to the **Request** panel on the left.
2. Inject the `"roleid": 2` key into the JSON body:

```http

  "email": "wiener@normal-user.net",
  "roleid": 2

```

> [!NOTE]
> Ensure the JSON syntax remains valid (include a trailing comma `,` after the `"email"` line). Burp Suite will automatically recalculate the `Content-Length` header.

1. Click **Send** in Repeater.
2. Inspect the **Response** panel. If the server replies with:
   ```json

     "username": "wiener",
     "email": "wiener@normal-user.net",
     "apikey": "4K2L8J...",
     "roleid": 2
   }
   ```

   The `roleid` parameter was successfully accepted and committed to the database!

### Step 7: Access the Administrative Panel

2. An **Admin panel** link (`/admin`) will now appear in the navigation bar.
3. Open `/admin` and execute administrative actions (such as deleting user `carlos`).

## 4. Backend Source Code: Vulnerable vs. Secure

### ❌ Vulnerable Implementation (Blind Object Auto-Binding)
```typescript
// Express / Node.js Route Handler
app.post("/my-account/change-email", authenticateUser, async (req, res) => {
  try {
    // ❌ DANGEROUS: Directly committing entire req.body into database!
    // Attackers can inject roleid, isAdmin, balance, or password hashes.
    const updatedUser = await db.user.update({
      where: { id: req.user.id },
      data: req.body, 
    });

    // ❌ Leaking internal sensitive properties back to the client
    return res.json(updatedUser);
  } catch (error) {
    return res.status(500).json({ error: "Failed to update profile." });
  }
});
```

---

### ✅ Secure Implementation (Strict DTO & Field Whitelisting)
```typescript
import { z } from "zod";

// 1. Define explicit validation schema (Only permit safe user fields)
const UpdateEmailSchema = z.object({
  email: z.string().email("Invalid email format"),
});

app.post("/my-account/change-email", authenticateUser, async (req, res) => {
  try {
    // 2. Validate input: Unknown fields (like roleid) are discarded / rejected
    const parsedData = UpdateEmailSchema.parse(req.body);

    // 3. Update database EXCLUSIVELY with whitelisted properties
    const updatedUser = await db.user.update({
      where: { id: req.user.id },
      data: {
        email: parsedData.email, // roleid CAN NEVER be modified from this route!
      },
      select: {
        id: true,
        username: true,
        email: true,
        // Do not expose roleid or password hashes in general profile responses
      },
    });

    return res.json({
      message: "Email updated successfully.",
      user: updatedUser,
    });
  } catch (error) {
    return res.status(400).json({ error: "Invalid input provided." });
  }
});
```

## 5. Prevention Summary & Best Practices

1. **Enforce Strict DTOs (Data Transfer Objects) & Whitelisting:**
   Always parse and filter client inputs with validation libraries (e.g. Zod, Joi, class-validator) or framework-level DTOs before touching the database layer.
2. **Never Accept Role Attributes from Public Endpoints:**
   Role assignments must only occur via dedicated administrative endpoints (e.g. `PATCH /api/admin/users/:id/role`) protected by strict RBAC middleware.
3. **Prevent Information Disclosure in Responses:**
   Do not return full database entities in API responses. Utilize response DTOs or field selection to omit sensitive attributes like `roleid`, `password_hash`, and permission flags.
