# Cross-Site Request Forgery (CSRF): Understanding the Flaw, Token Mechanisms, & Testing

Developers and web security learners often struggle with fundamental questions: **"Where is the actual bug in CSRF?"**, **"How do we test for it systematically?"**, and **"Are modern web apps using Bearer tokens still vulnerable to CSRF?"**

In simple terms, **Cross-Site Request Forgery (CSRF)** is a web security vulnerability where an attacker **tricks a victim's browser** into submitting unwanted state-changing requests (such as updating emails, changing passwords, or transferring funds) to an application where the victim is currently authenticated.

---

## 1. Where is the Bug? (Root Cause of CSRF)

CSRF arises from the combination of **inherent browser behavior (*Ambient Credentials*)** and a **server-side authorization flaw**:

### 1. Inherent Browser Behavior (Automatic Credential Attachment)
When a user logs into a website (e.g. `bank.com`), the server sets a **Session Cookie** stored inside the user's browser cookie jar.

Every time the browser initiates an HTTP request to `bank.com`—**even if that request originates from an entirely separate malicious website opened in another tab (e.g. `evil-hacker.com`)**—the browser automatically **attaches the user's valid session cookie for `bank.com`**!

### 2. The Server-Side Design Flaw (Blind Trust in Cookies)
If `bank.com`'s backend relies **solely on session cookies** to authorize incoming requests:
- The server inspects the request: *"Valid session cookie detected for User Alice!"*
- The server **CANNOT DISTINGUISH** whether Alice clicked a button on `bank.com` intentionally, or if Alice's browser was tricked into submitting the request in the background while visiting `evil-hacker.com`!

> [!IMPORTANT]
> **THE ROOT FLAW:** The server fails to verify **USER INTENT**. It validates user identity (*Who is sending this?* via Cookie), but ignores request origin and authorization intent (*Did the user deliberately trigger this action?*).

## 3. What is an Anti-CSRF Token & Why is it the Standard Defense?

To eliminate this vulnerability, the security community developed the **Anti-CSRF Token** (*Synchronizer Token Pattern*):

1. When a user navigates to a sensitive form (such as changing an email), the backend generates a **cryptographically random, unpredictable token** unique to that user's session.
2. This token is embedded directly into the HTML form as a hidden input element:
   ```html
   <input type="hidden" name="csrf" value="d9f83a2e1c0b47a9..." />
   ```
3. When the form is submitted, the server validates both parameters:
   - **Session Cookie:** Validates who the user is.
   - **CSRF Token Parameter:** Proves that the request was generated by a genuine form rendered by the application.

### Why Can't an Attacker on `evil.com` Steal the Victim's Token?
Because of the **Same-Origin Policy (SOP)** enforced by all web browsers! A script running on `evil.com` is strictly prohibited from reading the DOM, HTML contents, or HTTP responses of `target.com`. The attacker can trigger a submission, but cannot read or forge the victim's secret token.

## 4. Catalog of CSRF Token Implementation Flaws

Developers frequently introduce vulnerabilities when implementing custom CSRF token validations. Here are 4 common real-world flaws:

![CSRF Token Flaws](/images/csrf-token-flaws.svg)

---

### Flaw 1: Token Validation Depends on Request Method (POST vs GET)
Security middleware is configured to validate tokens strictly on `POST` requests. When requests are submitted via `GET`, token checks are skipped!

#### Testing & Exploitation:
Switch the exploitation form from `POST` to `GET`:
```html
<!-- Triggered automatically using a simple image tag -->
<img src="https://target.com/email/change?email=hacker@evil.com" />
```

---

### Flaw 2: Token Validation Depends on Token Presence
Some backend handlers evaluate tokens conditionally:
```javascript
// ❌ VULNERABLE: Only verifies token IF the parameter exists
if (req.body.csrf) {
  validateCsrfToken(req.body.csrf);
}
```

#### Testing & Exploitation:
In Burp Suite, **delete the `csrf` parameter completely** from the POST body. If the action succeeds with status `200 OK`, the application is vulnerable to *Token Presence* bypass!

---

### Flaw 3: Token is Not Tied to the User Session (Shared Global Pool)
The backend verifies that the submitted CSRF token exists within its valid database pool, but **FAILS TO VERIFY that the token belongs to the currently logged-in user**.

#### Case Study: Two-Account Testing (Wiener vs Carlos):
1. **Wiener (Attacker Account):** Log in to the target app, copy a valid CSRF token (`gTEZBeALZIzytDnGqldU17LemGrYRGax`).
2. **Carlos (Victim Account):** Log in using a separate browser session.
3. The attacker constructs an HTML form containing **Wiener's token** and triggers it in **Carlos's** browser:
   ```html
   <form action="https://target.com/my-account/change-email" method="POST">
     <input type="hidden" name="email" value="hacker@evil.com" />
     <input type="hidden" name="csrf" value="gTEZBeALZIzytDnGqldU17LemGrYRGax" />
   </form>
   ```
4. **Outcome:** Carlos's email updates successfully! The server validates the token against the global pool without verifying ownership.

---

### Flaw 4: Token Tied to Non-Session Cookie (`csrfKey` Injection)
The server binds the CSRF token to a separate tracking cookie (e.g. `csrfKey`) rather than the authenticated session.
If the application contains a secondary **Cookie Injection / CRLF Injection** flaw, an attacker can inject their own `csrfKey` into the victim's browser alongside their corresponding valid CSRF token.

## 5. Is CSRF Limited to HTML Form Inputs?

**The Answer: NO!**

While HTML forms (`<form>`) are the standard vector, CSRF vulnerabilities apply to **ANY state-changing request** where browsers automatically attach ambient credentials:

### 1. CSRF via URL / Media Tags (GET Requests)
```html
<img src="https://bank.com/transfer?to=hacker&amount=1000000" />
<a href="https://target.com/api/delete-account">Click here to claim a prize!</a>
```

### 2. CSRF on REST APIs & JSON Bodies (`enctype="text/plain"`)
If backend parsers accept JSON structures without strictly requiring `Content-Type: application/json`, HTML forms can forge JSON payloads:
```html
<form action="https://target.com/api/user/update" method="POST" enctype="text/plain">
  <input name='{"email":"hacker@evil.com", "ignore":"' value='test"}' type='hidden'>
</form>
```

### 3. CSRF on GraphQL Mutations
```html
<form action="https://target.com/graphql" method="POST">
  <input type="hidden" name="query" 
         value="mutation { changeEmail(newEmail: &quot;hacker@evil.com&quot;) { success } }" />
</form>
```

### 4. Cross-Site WebSocket Hijacking (CSWSH)
When establishing WebSockets (`wss://`), browsers transmit session cookies during the handshake phase, allowing attacker sites to hijack real-time communications.

### 5. Login & Logout CSRF
* **Logout CSRF:** Forcing users to log out unexpectedly.
* **Login CSRF:** Forcing a victim to log in to an attacker-controlled account to capture sensitive personal activity.

## 6. Modern Web: Are Bearer Tokens in Headers Vulnerable to CSRF?

When modern web applications authenticate requests via custom authorization headers:
```http
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
```

The application is **100% IMMUNE / SAFE against classic CSRF**, because:
1. Browsers **NEVER attach** custom `Authorization` headers automatically to cross-origin requests.
2. Attackers cannot read stored tokens from `localStorage` due to the **Same-Origin Policy (SOP)**.
3. Cross-origin requests with custom headers mandate a **CORS Preflight (`OPTIONS`)** check, which browsers block unless explicitly authorized.

### ⚠️ Three Gotchas in Modern Web Apps:
1. **JWT Stored in Cookies:** If tokens are transmitted via cookies (`Set-Cookie: token=...; HttpOnly`) rather than headers, the application **remains vulnerable to CSRF** unless protected by `SameSite=Lax/Strict`.
2. **The XSS vs CSRF Trade-off:**
   * Stored in `localStorage`: Immune to CSRF, but vulnerable to token theft via **XSS**.
   * Stored in `HttpOnly Cookie`: Immune to XSS theft, but requires protection against **CSRF**.
3. **CORS Misconfigurations:** Overly permissive origins (`Access-Control-Allow-Origin: https://evil.com` with credentials).

## 9. Backend Source Code: Vulnerable vs. Secure

### ❌ Vulnerable Implementation (Blind Cookie Reliance)
```typescript
import express from "express";
const app = express();
app.use(express.urlencoded({ extended: true }));

app.post("/my-account/change-email", (req, res) => {
  const sessionUser = req.cookies.session_user_id;

  // ❌ FATAL: Only verifies session existence, zero intent verification
  if (!sessionUser) {
    return res.status(401).send("Please log in.");
  }

  updateUserEmail(sessionUser, req.body.email);
  return res.send("Email updated successfully!");
});
```

---

### ✅ Secure Implementation (Session-Bound Cryptographic Token)
```typescript
import express from "express";
import crypto from "crypto";

const app = express();
app.use(express.urlencoded({ extended: true }));

// 1. Generate CSRF token bound strictly to user session
app.get("/my-account/profile", (req, res) => {
  const sessionId = req.cookies.session_id;
  const userSession = getSession(sessionId);

  if (!userSession.csrfToken) {
    userSession.csrfToken = crypto.randomBytes(32).toString("hex");
  }

  res.render("profile", { csrfToken: userSession.csrfToken });
});

// 2. Strict Token Validation on Sensitive State-Changing Endpoints
app.post("/my-account/change-email", (req, res) => {
  const sessionId = req.cookies.session_id;
  const userSession = getSession(sessionId);

  if (!userSession) {
    return res.status(401).json({ error: "Unauthorized session." });
  }

  const clientToken = req.body.csrf;

  // ✅ CRITICAL DEFENSE: Token is mandatory AND must match session token
  if (!clientToken || typeof clientToken !== "string" || clientToken !== userSession.csrfToken) {
    return res.status(403).json({ error: "Access denied: Invalid CSRF Token." });
  }

  updateUserEmail(userSession.userId, req.body.email);
  return res.json({ success: true, message: "Email updated securely." });
});
```

## 10. Modern Mitigation Strategies

1. **Enforce `SameSite=Lax` or `SameSite=Strict` Cookie Attributes:**
   Prevents browsers from attaching cookies to cross-origin requests.
2. **Deploy Built-in Framework Anti-CSRF Middleware:**
   Use established libraries (e.g. `csurf` in Node.js, Spring Security CSRF in Java, or Django's `{% csrf_token %}`).
3. **Require Custom Request Headers for Single Page Applications:**
   Requiring headers such as `X-Requested-With` or `X-CSRF-Token` ensures standard HTML form submissions from other origins are blocked by default.
4. **Require Re-Authentication for Critical Operations:**
   Prompt users to enter their existing password before updating credentials or authorizing fund transfers.
